## Оценка угроз и направления для улучшения backend

Этот документ описывает основные потенциальные угрозы и возможные направления развития
безопасности и архитектуры backend-микросервисов TensorTalks.

---

### 1. Хранение и управление токенами

- **Текущее состояние**
  - Access/refresh JWT подписываются симметричным секретом (HS256).
  - Refresh-токены не хранятся в базе, их отзыв возможен только через смену секрета.
  - Проверка токенов централизована в `auth-service`.

- **Потенциальные угрозы**
  - При компрометации `jwt.secret` атакующий может выпускать валидные токены.
  - Отсутствие индивидуального хранения refresh-токенов усложняет точечный отзыв сессий.

- **Рекомендации**
  - Ввести таблицу `refresh_tokens` (или аналог) с возможностью отзыва/ротации токенов per user/device.
  - Реализовать механизмы ротации секрета (key id + несколько активных ключей).
  - Добавить ограничение по числу одновременных активных сессий на пользователя.

---

### 2. Управление паролями и политиками аутентификации

- **Текущее состояние**
  - Пароли хешируются с помощью bcrypt (`bcrypt.DefaultCost`).
  - Минимальная длина пароля — 6 символов, без политики сложности.

- **Потенциальные угрозы**
  - Слабые пароли повышают риск успешного brute-force/credential stuffing.
  - Отсутствует блокировка/замедление при множественных неудачных попытках логина.

- **Рекомендации**
  - Ужесточить политику паролей (минимальная длина, символы разных категорий).
  - Добавить rate limiting / CAPTCHA / временную блокировку при серии неудачных логинов.
  - Ввести аудит событий аутентификации (успех/ошибка, IP, user-agent) с агрегацией.

---

### 3. Защита HTTP-API и CORS

- **Текущее состояние**
  - BFF настраивает CORS через `cors.allow_origins` и `cors.allow_headers`.
  - Отладочный эндпоинт `/debug/users` в `user-store-service` помечен как внутренний и не проксируется BFF.

- **Потенциальные угрозы**
  - Ошибка в конфигурации CORS может открыть API для нежелательных origin.
  - Неправильная публикация сервисов (например, прямой доступ к `user-store-service` снаружи) может
    открыть чувствительные эндпоинты (`/debug/users`, CRUD над пользователями).

- **Рекомендации**
  - Жёстко ограничить `AllowOrigins` до конкретных доменов (убрать `*` в проде).
  - На уровне инфраструктуры (reverse-proxy/ingress) публиковать только BFF, остальные сервисы — в приватной сети.
  - Добавить аутентификацию/авторизацию даже к отладочным эндпоинтам (или отключать их сборкой/флагом).

---

### 4. Валидация входных данных и нормализация логинов

- **Текущее состояние**
  - Логины нормализуются (trim + lowercase), проверяется длина и отсутствие пробелов.
  - Фронтенд дополнительно запрещает e-mail и персональные данные в логине, но это правило не дублируется на backend.

- **Потенциальные угрозы**
  - Различие в правилах валидации между фронтом и backend может привести к инъекциям/неконсистентности.
  - Отсутствие строгой валидации формата логина (разрешённые символы) на backend.

- **Рекомендации**
  - Синхронизировать правила валидации логина на backend с тем, что реализовано на фронтенде
    (разрешённые символы, запрет e-mail/телефонов и т.п.).
  - Добавить централизованный модуль/пакет валидации, используемый всеми сервисами.

---

### 5. Логирование и наблюдаемость

- **Текущее состояние**
  - Используется стандартный `log` для ошибок в точках входа и некоторых хендлерах.
  - Нет единой структуры логов и кореляции запросов (trace id / request id).

- **Потенциальные угрозы**
  - Сложность расследования инцидентов (невозможно связать цепочку запросов через микросервисы).
  - Риск утечки чувствительных данных в логи при неаккуратной отладке.

- **Рекомендации**
  - Ввести единый формат логов (JSON) и кореляционные идентификаторы (request-id, trace-id).
  - Стандартизировать уровни логов (info/warn/error) и поля (service, endpoint, user_id, status).
  - Исключить из логов пароли, токены и другие чувствительные данные.

---

### 6. Масштабирование и отказоустойчивость

- **Текущее состояние**
  - Сервисы поддерживают graceful shutdown и health-check `/healthz`.
  - Используется одна PostgreSQL-база для учётных записей.

- **Потенциальные угрозы**
  - Один кластер PostgreSQL — единая точка отказа без репликации/фейловера.
  - При росте нагрузки `auth-service` и `user-store-service` могут стать узким местом.

- **Рекомендации**
  - Добавить репликацию PostgreSQL и мониторинг (метрики, алёрты).
  - Применить горизонтальное масштабирование сервисов через оркестратор (Kubernetes, Nomad и т.п.).
  - Ввести circuit breaker / retry-политику между микросервисами (особенно между auth и user-store).

---

### 7. Авторизация и роли (на будущее)

- **Текущее состояние**
  - Сейчас реализована только аутентификация (подтверждение личности пользователя).
  - Роли/права доступа не описаны и не зашиты в JWT.

- **Потенциальные угрозы**
  - При расширении функционала (HR-кабинеты, админки и т.п.) отсутствующая модель прав
    может привести к ошибкам авторизации.

- **Рекомендации**
  - Спроектировать модель ролей (user, admin, hr, team_lead и др.).
  - Добавить роль/права в claims JWT или в отдельный сервис авторизации.
  - Ввести промежуточный слой авторизации (middleware) в BFF и доменных микросервисах.

---

Этот документ не исчерпывающий, но задаёт направления для дальнейшего усиления безопасности
и масштабируемости системы при развитии продукта за рамки MVP.
